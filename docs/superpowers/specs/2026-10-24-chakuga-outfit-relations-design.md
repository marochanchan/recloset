# 着画とコーデ関係DB 設計書

- 作成日: 2026-10-24（2026-10-25 に Codex レビューの指摘を反映）
- 対象: Re:Closet（`/Users/marochan/gs-works/recloset`）
- 状態: Codex（Astra）レビュー反映済み → 開発プラン

## 1. 目的

これまでの Re:Closet は、床や机に置いた服の写真（平置き）で服を管理するアプリだった。今回は、鏡の前で撮った**着画**（写真と数秒の動画）とスマホの外出写真を取り込み、**服と服の関係DB**と**コーデ履歴**を作る。

- 今回の中心は、画面よりも**データの構造**。「いつ、どの服を一緒に着たか」を貯め、よく着る組み合わせ、1着から別の服をたどる、季節の比較など、いろいろな角度から使えるようにする。
- コンセプト：**ごちゃごちゃのクローゼットを全部登録すると、つながりのマップで遊べるようになる。だから撮影のやる気が上がる。**
- 優先順位：かっこいい・使いたい・手間が少ない（UX）が先。AIの費用と事業モデルは二の次。

### 成功の基準

1. 鏡の前（開発機の Mac ＋ Web カメラ）で撮影すると、AI が写っている服を見分けて手持ちの服の候補を出す。合っていれば「確定」1回でコーデとして記録できる。
2. スマホの外出写真・動画を取り込むと、撮影日のコーデとして記録できる。
3. 服の詳細ページの「つながりのマップ」で、一緒に着た服をたどれる。つながりが育つ様子を再生できる。
4. AI の候補と最終的な選択が記録され、1位の候補の正解率を測れる。
5. 2026-11-10 までに、GGA のデモに必要な機能が本番環境で通しで動く（12章）。

## 2. 前提と将来の構想

### 今のアプリ（関係する部分）

- 服：`clothing_items`、`clothing_images`（Supabase Storage、本人だけが見られるバケット）。カテゴリーは `lib/clothing-options.ts` の `CATEGORY_OPTIONS`（tops / bottoms / dress / outer / shoes / bag / other）。服の属性として DB に保存しているのは `subcategory` と `main_color`（migration 013）。柄は保存していない。
- 着用記録：`wear_logs`（服1着ごとの記録）。「今日着た」は `app/(main)/protected/items/[id]/actions.ts` の `recordWearToday` が `wear_logs` に直接書き込み、そのあと `clothing_items.wear_count` と `last_worn_at` を更新している（「将来RPC化するTODO」あり）。
- 書き込み権限：migration 002 で、`authenticated` は `clothing_items`、`clothing_images`、`wear_logs` を直接、追加・更新・削除できる。
- 服の削除：`deleteClothingItem` は完全に削除する。`wear_logs` も on delete cascade で消える。DB を消したあと、Storage の画像も消している。
- 服の直接削除はほかにもある。登録に失敗したときに、作ったばかりの服を消す処理だ（`components/clothing-item-form.tsx`、`lib/photo-batch-registration.ts`）。
- 行動履歴：migration 019 は、例外としてトリガーで `closet_activity_events` に記録している。`wear_logs` への追加ごとに、記録した時刻（`now()`）で1件残る。服を削除しても、行動履歴は `clothing_item_id = null` で残る。
- Re:Quest の「着る」は `wear_logs.worn_at`（着た日）で数える（`lib/re-quest-query.ts`）。Re:Garden は行動履歴の `occurred_at`（記録した日）で数える。
- 公開：`clothing_items` には「公開中なら `published_at` がある、非公開なら null」という CHECK 制約がある（migration 008）。
- 関数の権限：今のマイグレーションは、関数を作ったら `revoke all on function ... from public, anon, authenticated` で取り上げてから、必要なロールにだけ許可している。
- AI：平置き写真1枚から服1着を解析する（`lib/clothing-image-analysis.ts`、Vercel AI Gateway 経由の `google/gemini-3.5-flash-lite`）。解析結果は保存していない。
- 写真の前処理：`lib/image-processing.ts`。アップロード用は長辺1600px・JPEG・品質0.85、AI 解析用は長辺1024px。
- Today のコーデ候補：`status` が closet か candidate で、カテゴリーが tops / bottoms / dress / outer の服を対象にしている（`app/(main)/today/page.tsx`）。
- テスト：`node --test scripts/test-*.mts`（Node 標準のテスト機能、Supabase はモック）と、Docker の Postgres で動かす `supabase/tests/run-0XX.sh`。

### 将来の構想（今回は作らないが、邪魔しない設計にする）

- Web カメラ内蔵の鏡（姿見）デバイスと、ローカル GPU の AI パソコンを組み合わせて売る。ユーザー側の AI はローカルで動き、クラウドはデータと保存先の同期先になる。サービス側の AI はクラウドに置く。

## 5. 用語

| 用語 | 意味 |
|---|---|
| 着画 | 服を着た姿の写真・動画。鏡の前で撮るものと、スマホの外出写真がある |
| コーデ | 1回分の組み合わせ（`outfits`）。写真がなくても作れる |
| 確認待ち／確定 | コーデの状態。確定したコーデだけを集計に入れる |
| 自動の関係 | コーデ履歴から計算する関係（一緒に着た回数、最後に一緒に着た日、よく着る組み合わせ） |
| 自分で付ける関係 | セットアップ、色違い・同じ型。グループとして持つ |
| 入れ替え候補 | 同じカテゴリーで、合わせる相手がかぶる服 |
| 出番待ちの服 | 登録済みで、まだどの服ともつながっていない服 |
| 最近 | 今日を含む直近90日 |
| 季節 | 春3〜5月、夏6〜8月、秋9〜11月、冬12〜2月 |
| 着た日／記録した日 | 着た日はコーデの `worn_on` と着用記録の `worn_at`（Re:Quest が使う）。記録した日は行動履歴の `occurred_at`（Re:Garden が使う）。過去の写真を今日取り込むと、2つは別の日になる。今回はこの分け方をそのまま使う |

## 6. データベース

### 6.1 テーブル

新しいテーブルはすべて `user_id`、UUID の主キー（関連表を除く）、`created_at`、`updated_at` を持つ。日付の区切りは**日本時間**で統一する。

**`outfits`**（コーデ1回分）

| 列 | 内容 |
|---|---|
| `worn_on` | 着た日（date、日本時間） |
| `source` | `mirror`（鏡で撮影）／`upload`（アップロード）／`manual`（写真なし）／`wear_suggestion`（「今日着た」からの提案） |
| `status` | `pending`（確認待ち）／`confirmed`（確定） |
| `revision` | 版番号。確定・編集のたびに1増える。古い版をもとにした送り直しを拒否するために使う |
| `client_request_id` | 下書きを作るときの依頼ID。`(user_id, client_request_id)` で一意 |
| `analysis_media_id` | AI が解析する代表の写真（`outfit_media`） |
| `current_analysis_run_id` | 今有効な解析（`outfit_analysis_runs`） |
| `selected_person_index` | 写真に複数人いるとき、本人として選んだ人の番号 |
| `note` | メモ |
| `confirmed_at` | 確定した日時 |

**`outfit_media`**（着画の写真・動画）

| 列 | 内容 |
|---|---|
| `id` | ブラウザがファイルごとに作る UUID。送り直しても変わらないので、二重登録を防ぐ鍵になる。サーバーは、すでにある ID なら本人の行かを確かめて、その続きとして扱う |
| `outfit_id` | どのコーデか |
| `kind` | `photo`／`video`／`frame`（動画から作った解析用の静止画） |
| `provider` | `cf_images`／`cf_stream`。将来、別の保存先に移せるようにする |
| `provider_asset_id` | Cloudflare 側の ID。**サーバーがアップロード URL を発行したときに受け取って保存する**。クライアントから受け取ったり、付け替えたりはしない。`(provider, provider_asset_id)` で一意 |
| `upload_attempt` | アップロードの試行回数（1から） |
| `upload_expires_at` | アップロード URL の期限 |
| `status` | `uploading`／`processing`（動画の変換中）／`ready`／`failed` |
| `width`、`height`、`duration_sec` | 大きさと長さ |
| `taken_at` | 撮影日時（EXIF、読めなければ null） |
| `sort_order` | 並び順 |

**`outfit_items`**（コーデに入っている服）← 関係DBの中心

| 列 | 内容 |
|---|---|
| `outfit_id`、`item_id` | 主キーはこの2つ。`item_id` の外部キーは **on delete restrict**（6.5 章） |
| `wear_log_id` | ひも付く着用記録 |
| `source` | `detected`（AI の認識から）／`manual`（手で追加） |
| `detection_id` | もとになった AI の認識結果（あれば） |

**`outfit_analysis_runs`**（解析の実行1回分）

| 列 | 内容 |
|---|---|
| `outfit_id`、`media_id` | どのコーデの、どの写真を解析したか |
| `status` | `queued`／`running`／`done`／`failed`／`canceled`（代表の写真を変えたなどで、途中でやめた） |
| `created_at`、`started_at`、`deadline_at`、`finished_at` | 作成、開始、期限、終了。`deadline_at` は作った時点で決める（`queued` のまま止まっても期限が来る） |
| `detector_model`、`compare_model` | 使ったモデル |
| `error` | 失敗の理由 |

- 1つのコーデで `queued` か `running` の実行は1つまで（部分一意インデックス）。
- 再解析しても古い実行は消さない（履歴として残す）。画面に出すのは `outfits.current_analysis_run_id` の実行の結果だけ。

**`outfit_detections`**（AI が見つけたもの1つ1つ）← 知見の記録

| 列 | 内容 |
|---|---|
| `run_id`、`outfit_id`、`media_id` | どの実行で、どのコーデの、どの写真か |
| `person_index` | 写っている人の番号 |
| `bbox` | 写真の中の位置。0〜1 に正規化した x, y, w, h |
| `category`、`subcategory`、`color`、`pattern` | AI が出した属性（柄は記録するだけ） |
| `candidates` | jsonb。`[{item_id, score, reasons[], rule_rank, compare_rank}]`。服が削除されて ID が残っていても、画面は「削除した服」と出す |
| `decision` | `matched`（照合した）／`registered`（新しく登録した）／`ignored`（無視した）／`not_me`（本人以外）／null |
| `chosen_item_id` | 自分が選んだ服。外部キーは on delete set null |
| `chosen_rule_rank`、`chosen_compare_rank`、`decided_at` | 選んだ服が、ルールで何位、見比べ後に何位だったか、選んだ日時 |

**`item_groups`** と **`item_group_members`**（自分で付ける関係）

- `item_groups.kind`：`setup`（セットアップ）／`same_model`（色違い・同じ型）。種類はあとから増やせる。
- `item_group_members` は `(group_id, item_id, kind)` を持つ。`(user_id, item_id, kind)` で一意にして、1着が入れるのは種類ごとに1グループまでにする。`kind` は `(group_id, kind)` の複合外部キーでグループと一致させる。

**月ごとのサマリー**（2層目）

| テーブル | 1行の単位 | 列 |
|---|---|---|
| `item_monthly_stats` | 服1着 × 1か月 | `wear_log_count`（着用記録の件数）、`worn_days`（着た日数。同じ日の重複は1日）、`outfit_count`（確定コーデに入った回数）、`last_worn_on` |
| `item_pair_monthly_stats` | 服2着（`item_a < item_b`）× 1か月 | `outfit_count`、`together_days`、`last_worn_on` |
| `outfit_combo_monthly_stats` | 服の組み合わせ一式 × 1か月 | `combo_key`（並べ替えた服 ID のハッシュ）、`item_ids`（uuid[]）、`outfit_count`、`last_worn_on` |

- 一意キー：`(user_id, item_id, month)`、`(user_id, item_a, item_b, month)`、`(user_id, combo_key, month)`。
- `month` は月の1日の date（日本時間）。
- 服への外部キーは on delete cascade。

**`media_deletion_queue`**（Cloudflare の削除待ち）

- `provider`、`provider_asset_id`、`attempts`、`next_attempt_at`、`claim_token`、`lease_until`、`last_error`、`done_at`。
- メディアを DB から消すときは、**同じトランザクションで必ずここに入れる**（失敗したときだけではない）。実際の削除は 6.6 章の処理が行う。

**既存テーブルの変更**

- `clothing_items` に `archived_at` を足す（6.5 章）。あわせて `check (archived_at is null or not is_public)` を足し、しまった服は公開できないことを DB で保証する。
- `wear_logs` に `source`（`wear_today`／`outfit`）を足す。今ある行は `wear_today` にする。
- カテゴリーに「小物」（`accessory`）を足す。カテゴリーはアプリ側で管理しているので、テーブルの変更は要らない。ただし次の4か所をまとめて変える作業になる。種類は、スカーフ・ストール、帽子、ベルト、その他。
  - `lib/clothing-options.ts` のカテゴリーと種類の一覧
  - `lib/clothing-image-analysis.ts` の AI の出力スキーマ
  - 登録・編集の検証
  - Today の候補の対象外リスト

### 6.2 書き込みはすべて RPC を通す

サマリーがずれないように、サマリーの元になるデータと派生値（`wear_count`、`last_worn_at`、サマリー）の書き込みは、すべて RPC（DB の関数）を通す。**新しいトリガーは作らない。** 019 の行動履歴のトリガーはそのまま残す。

| RPC | 内容 |
|---|---|
| `create_outfit_draft` | 確認待ちのコーデを作る。同じ `client_request_id` なら前回と同じ結果を返す |
| `register_outfit_media` | メディアの行を作り、サーバーが受け取った Cloudflare の ID を保存する（サーバー専用。6.3 章） |
| `confirm_outfit` | 服の一覧・日付・メモと、もとにした版番号（`expected_revision`）を受け取り、確定・編集する |
| `delete_outfit` | コーデを消す。メディアは削除待ちに入れる |
| `record_wear_today` | 今の「今日着た」を置き換える |
| `archive_item`／`unarchive_item` | 服をしまう／戻す |
| `hard_delete_item` | 服を完全に削除する（6.5 章） |
| `set_item_group` | 自分で付ける関係を作る、変える |
| `rebuild_monthly_stats(user, month)` | その月のサマリーを、その月の事実から作り直す（内部用） |
| `rebuild_all_stats(user)` | 全期間を作り直す（内部用。初期集計と万一のため） |

**RPC の2つの種類**

| 種類 | 呼ぶ人 | ユーザーの決め方 | 実行の権限 |
|---|---|---|---|
| ユーザー向け | ログインしたユーザー（画面から） | `auth.uid()`。引数ではユーザーを受け取らない | `authenticated` |
| サーバー専用 | サーバー（`service_role`）：メディアの登録と状態、webhook、削除待ち、解析結果の保存、初期集計 | 保存済みの行（メディア、コーデ）から持ち主を導く。メディアの登録のように行がまだないときだけ `p_user_id` を受け取る。その値は、サーバーがログインのセッションで確かめたもの | `service_role` だけ |

**すべての RPC で守ること**

- `security definer` にし、`search_path` を `''` に固定する。
- 作ったら、同じトランザクションの中で `revoke all on function ... from public, anon, authenticated` してから、上の表のロールにだけ `grant execute` する。PostgreSQL では新しい関数を誰でも（`PUBLIC`）実行できるため、`authenticated` と `anon` から取り上げるだけでは足りない。内部用の関数（作り直しなど）は、どのロールにも許可しない。
- 最初に、決まった持ち主でユーザーごとのロック（`pg_advisory_xact_lock`）をかける。変更前の状態は、ロックを取ったあとに読む。同じユーザーの更新は1つずつ順番に処理する。
- 参照するデータすべて（服、着用記録、メディア、認識結果、コーデ）が本人のものか確かめる。さらに、**同じ本人の別のコーデのもの**を混ぜていないかも確かめる。外部キーで保証できる部分は外部キーでも縛る。
- サマリーは「1を足す・1を引く」ではなく、**変更があった月だけを作り直す**。影響する月は変更の前に集めておく。日付を別の月に直したときは、元の月と新しい月の両方を作り直す。
- 作り直しは「その月の行を消してから、事実から入れ直す」。元の事実がゼロになった月は、行が残らない。
- 書き込みとサマリーの作り直しは、1つのトランザクションで行う。

**`confirm_outfit` と着用記録**

| 場面 | 処理 |
|---|---|
| 初めての確定 | 服ごとに着用記録を用意する。同じ日に、まだどのコーデにもつながっていない `wear_today` の記録があれば、それを使う。なければ `source = outfit` の記録を新しく作る |
| 同じ内容の送り直し | `expected_revision` が今の版と同じで、中身も同じなら、何もせずに今の結果を返す。同じコーデにつながっている記録はそのまま使う |
| 古い版からの送り直し | `expected_revision` が今の版より古ければ拒否し、今の状態を返す。訂正が巻き戻らない |
| 服を足す | 初めての確定と同じ |
| 服を外す | `source = outfit` の記録は消す。使っていた `wear_today` の記録は、つながりを外すだけで残す |
| 日付を変える | `source = outfit` の記録は、`worn_at` を新しい日付に直す。使っていた `wear_today` の記録は、つながりを外して残し、新しい日付で `source = outfit` の記録を作る |

- 過去の日付の記録の `worn_at` は、その日の 12:00（日本時間）にする。今日なら今の時刻にする。
- 影響した服の `wear_count` と `last_worn_at` は、**残っている着用記録から計算し直す**（件数と最新の `worn_at`）。最新の着用を過去の日付に直した場合も、正しい最新日になる。
- 019 のトリガーは、着用記録を**追加**したときだけ動く。
  - `source = outfit` の記録の日付を直すだけなら、行動履歴は増えない。
  - `wear_today` の記録を外して新しく記録を作る場合は、1件増える。
- 過去の写真を今日取り込むと、次のようになる。今回はこの分け方のまま変えない。
  - Re:Garden（記録した日）では今日の行動になる。
  - Re:Quest（着た日）では過去の日の「着る」になる。

### 6.3 アクセス権限

| 対象 | `authenticated` が直接できること | それ以外の書き込み |
|---|---|---|
| `clothing_items` | 読む、削除。追加と更新は、`wear_count`、`last_worn_at`、`archived_at` **以外**の列だけ（列ごとの権限にする。追加のときの派生値は DB の初期値 0 と null になる） | 派生値とアーカイブは RPC |
| `clothing_images` | 今までどおり | ― |
| `wear_logs` | 読むだけ | RPC |
| `outfits`、`outfit_items`、`outfit_media`、`outfit_analysis_runs`、`outfit_detections` | 読むだけ（本人の行） | RPC。解析結果の保存はサーバーが `service_role` で行う |
| `item_groups`、`item_group_members` | 読むだけ | RPC |
| サマリー3つ | 読むだけ | RPC の中から |
| `media_deletion_queue` | なし | RPC とサーバー |

- RPC の `execute` は 6.2 章の表のとおり。どの関数も最初に `public, anon, authenticated` から取り上げる。
- **服の直接削除は残す**（Codex のレビューで検討し、残すと決めた）：
  - 外部キーの on delete restrict で、コーデに入っている服は消せない。
  - 消せるのは、コーデに入っていない服だけになる。その服の着用記録とサマリーの行は cascade で一緒に消え、2着の関係とコーデのサマリーは元からないので、集計はずれない。
  - 起きるのは、ユーザーが自分で消した服の写真が Storage に残ることだけ。
  - 今ある2つの登録取り消し（`components/clothing-item-form.tsx`、`lib/photo-batch-registration.ts`）をデモの前に作り直す危険のほうが大きいので、RPC には移さない。
- RLS は、今までと同じく本人の行だけにする。アーカイブした服を RLS で隠すことはしない（履歴に必要なため）。
- 公開（サブプロジェクト2）は、あとで別の RPC として足す。

### 6.4 読み出しと期間

- Looks の着画の一覧とカレンダーは、表示している月の詳細の履歴（`outfits`、`outfit_items`）を読む。詳細の履歴は消さないので、古い月もそのまま読める。
- 「よく着る組み合わせ（最近）」は、直近90日の詳細の履歴から数える。
- **月の途中を含む期間**は、丸ごと入る月をサマリーで、端の途中の月を詳細の履歴で数える。季節の比較で「今年の9/1〜10/24」と「去年の9/1〜10/24」を比べるときも、去年の10/25〜31は入らない。
- 季節の比較の数値：服は**着た日数**、組み合わせは**コーデの回数**。
- 服の詳細ページのマップは、選んだ期間の2着の組み合わせの回数（`outfit_count`）を使う。「入れ替え」と「広がり」も同じデータから計算する。
- マップの**再生**は「つながりが育つ様子」を見せる。最初の記録から今日まで、累計の関係を週ごとに進める（記録の期間が4週より短ければ日ごと）。詳細の履歴から計算する。
- 計算の部分は、データを渡すと結果が返るだけの関数（純粋な関数）として `lib/` に置き、DB を使わずにテストする。

**導入時の初期集計**

- マイグレーションのあとに `rebuild_all_stats` を全ユーザーで実行し、今ある `wear_logs` から `item_monthly_stats` を作る。
- 今の `wear_count`、`last_worn_at` と着用記録が一致しているかを確かめ、ずれがあれば記録に合わせる（ずれた件数はログに残す）。
- 服1着ごとの着用記録から、過去のコーデや2着の関係を推測して作ることはしない。2着の関係とコーデのサマリーは空から始まる。

### 6.5 アーカイブと完全な削除

**しまう（アーカイブ）**

| 画面・機能 | しまった服の扱い |
|---|---|
| Closet の一覧と件数、Today の候補、見直し、AI の候補、写真なしの記録の選択画面、出番待ち | 出さない |
| Loop | 公開をやめる（`is_public = false`、`published_at = null` を同時に）。戻しても自動では公開しない。古い画面から公開しようとしても、6.1 章の CHECK 制約で失敗する |
| 過去のコーデ、Looks、季節の比較、マップ、集計 | 残す。マップでは「しまった服」の印を付ける |
| 服の詳細ページ | 履歴からは開ける。「戻す」ボタンを出す |
| Closet の絞り込み | 「しまった服」で一覧でき、そこから戻せる |

**完全に削除**（`hard_delete_item`）

1. 影響する月（その服の着用記録とコーデの月）を、削除の前に集める。
2. その服の `outfit_items` の行だけを消す。**コーデ（`outfits`）は消さない**ので、ほかの服どうしの組み合わせは残る。服がゼロになったコーデも、着画と一緒に残り、詳細に「服が登録されていません」と出る。
3. 服を消す。着用記録、服の写真の行、サマリーの行は cascade で消える。認識結果の `chosen_item_id` は null になる。行動履歴は今までどおり残る。
4. 集めた月のサマリーを作り直す（組み合わせのキーも作り直される）。
5. RPC が成功したら、サーバーが今までどおり Supabase Storage の服の写真を消す（今の `deleteClothingItem` の処理を引き継ぐ）。

- `outfit_items.item_id` は on delete restrict にする。コーデに入っている服を、RPC を通さずに直接削除しようとしても DB が拒否する。登録失敗の取り消し（作ったばかりの服の削除）は今までどおり動く。
- 画面では「完全に削除」は「しまう」とは別の操作にし、「過去の記録からも消えます」と警告する。

**コーデを消す**（`delete_outfit`）：`outfit_items` と、そのコーデが作った `source = outfit` の着用記録を消す。使っていた `wear_today` の記録は残す。メディアは削除待ちに入れ、サマリーを作り直す。

### 6.6 Cloudflare の削除待ちの処理

- 処理する人：サーバーの処理 `processMediaDeletionQueue`。
- 動くタイミング：
  - メディアを消す RPC が成功したあと（`after()` で）
  - アプリを開いたとき（1日1回まで）
  - Vercel Cron（1日1回）
- Cloudflare の削除 API を呼ぶ。404（もう存在しない）は成功として扱う。
- 失敗したら `attempts` を増やし、`next_attempt_at` を延ばす（1分、10分、1時間、1日）。10回失敗したらログに残して止める。
- 二重に動いても大丈夫なように、取り出しと結果の書き込みを分ける。
  - 取り出すとき：`for update skip locked` で選び、新しい `claim_token` と `lease_until`（5分後）を書き込む。
  - 結果を書き込むとき：同じ `claim_token` を持つ処理だけが書き込める。トークンが違えば何もしない。
  - 処理が途中で止まっても、`lease_until` を過ぎれば別の処理が取り出せる。

## 7. 取り込みと AI の流れ

### 7.1 記録の入口

- どの画面でも、右下に「＋記録」ボタンを出す。押すと次の4つから選べる。前回使った方法には「前回」の印を付ける。
  1. その場で撮影する
  2. 写真・動画から取り込む
  3. 写真なしで記録する
  4. 「今日着た」から提案する
- Today の一番上に「今日のコーデを記録」カードを出す。まだ記録していない日だけ表示し、記録したらその日の着画に変わる。

### 7.2 撮影（Mac ＋ Web カメラ）

- カメラを選べるようにする（Mac 内蔵のカメラと外付けの Web カメラ）。
- 映像は**鏡と同じ左右反転**で映す。保存する写真は反転を戻し、ロゴなどが正しい向きになるようにする。
- 「撮影」を押すと、5秒のカウントダウン（画面表示と音）のあと写真を撮り、続けて約5秒の動画を録画する。撮ったものを見て「保存」か「撮り直し」を選ぶ。
- 録画の形式は、ブラウザが対応していれば MP4（H.264）、対応していなければ WebM にする。どちらも Stream が変換する。
- 「撮影を始める合図」は差し替えられる部品にする（今はボタン、将来は音声やリモコン）。
- 「撮影待機」の全画面モード：カメラを常に表示し、ボタンは1つだけにする。
- カメラが使えない、または録画できないブラウザでは、写真だけ撮るか、アップロードに切り替える。

### 7.3 アップロード（スマホの外出写真など）

- 写真と動画をまとめて選べる。1つのコーデに複数の写真・動画を付けられる。
- 写真は、送る前にブラウザで撮影日（EXIF）を読み取り、コーデの日付の初期値にする。読めないときは手で入力する。
- 着画の写真は、**着画専用の設定**（長辺2560px、JPEG、品質0.9）で縮小し直してから送る。服の写真用の設定（1600px）は使わない。小さな小物まで切り出せるようにするため。位置情報などのメタデータは消える。
- 動画の長さの上限は60秒にする。
- **動画だけ**を取り込んだ場合は、Stream の変換が終わったあと、サーバーが動画の真ん中の静止画を取り出し、Images に `frame` として保存する。それを代表の写真として解析する。

### 7.4 保存（Cloudflare）

**流れ**

1. `create_outfit_draft` で、確認待ちのコーデを作る。
2. ブラウザはファイルごとにメディア ID（UUID）を作り、送り直しでも同じ ID を使う。
   - 同じメディア ID で「開始」がもう一度来たときは、新しいメディアを作らず、下の「送り直し」と同じ処理をする。
   - これで、URL を発行したあとに応答だけが失われた場合も、二重にならない。
3. メディア1つごとに、サーバーが本人のコーデか確かめてから、Cloudflare の**一度だけ使えるアップロード URL**（Images と Stream の Direct Creator Upload）を発行する。
   - そのとき Cloudflare が返す ID を、`register_outfit_media` でサーバーが DB に保存する。
   - Cloudflare 側の記録（メタデータ）にもユーザー ID とメディア ID を入れる。動画の長さの上限（`maxDurationSeconds`）もここで決める。
   - URL を発行したあと DB への保存に失敗したら、その ID をすぐ削除しにいく（失敗しても、アップロードされないまま期限切れになる下書きなので、データは残らない）。
4. ブラウザから Cloudflare へ直接送る。サーバー（Vercel）を大きなファイルが通らない。
5. 送り終わったとブラウザが知らせてきたら、サーバーが **Cloudflare の API で実体を確かめる**。ブラウザの申告だけで完了にはしない。
   - 写真：下書き（draft）でなくなっていれば `ready` にする。
   - 動画：受け取りが確認できたら `processing` にし、変換が終わったら `ready` にする。

**送り直し**

- 再送の前に、サーバーが今の試行の実体を Cloudflare で確かめる。
- すでに届いていれば、それを使う。応答だけが失われた場合もこれで救える。
- 期限切れか失敗なら、試行回数を1増やして新しい URL を発行し、新しい ID に置き換える。古い ID は削除待ちに入れる。

**動画の変換完了の通知（webhook）**

- 本文はそのまま（生のまま）読み、`Webhook-Signature` の時刻と本文から HMAC-SHA256 を計算して、定数時間で比べる。
- 時刻が5分より古いものは拒否する。
- 動画の ID が、そのメディアの**今の** `provider_asset_id` と一致するときだけ状態を変える。古い試行の通知や、同じ通知の2回目は、何も変えずに 200 を返す。
- 開発機のように通知が届かない環境のために、画面を開いたときに Stream の API で状態を確かめる処理も用意する。

**解析を始める条件**

- 代表の写真（`analysis_media_id`）が `ready` になったら、すぐ解析を始める。動画の変換の完了は待たない。
- 写真がなく動画だけなら、7.3 章の静止画ができてから始める。
- 動画の失敗は、解析とコーデの記録を止めない。

### 7.5 AI の解析（裏で進める）

**実行のしかた**

- Next.js の `after()` で、レスポンスを返したあとに解析を進める。画面を閉じても解析は進む。
- 実行1回ごとに `outfit_analysis_runs` を作り、作った時点で `deadline_at` を決める。ルートの `maxDuration` より短い、内部のタイムアウトを設ける。
- 結果を保存するときは、その実行が今もコーデの `current_analysis_run_id` で、`running` のときだけ保存する。遅れて返ってきた古い結果は捨てる。
- **期限切れの実行の扱い**：`after()` が始まる前や途中で強制終了され、`queued` か `running` のまま残った場合に備える。
  - 期限を過ぎた `queued`・`running` は、画面を開いたときや次の操作のときに `failed` にする。そのあと「もう一度解析」を出す。
  - これで「1つのコーデで実行中は1つまで」の制約に引っかからない。
- **代表の写真を変える・もう一度解析する**：1つのトランザクションで、次の3つをまとめて行う。
  1. 今の実行が `queued` か `running` なら `canceled` にする。
  2. 新しい実行を作る。
  3. `current_analysis_run_id` を新しい実行にする。
- 失敗したら「もう一度解析」か「手で選ぶ」を選べる。

**解析する写真**

- 代表の写真1枚だけを解析する。最初の写真を代表にし、あとから変えられる（変えると新しい実行になる）。
- 足りなければ「この写真も解析」で追加の実行をする。追加の写真で見つかった服が、すでにコーデに入っている服と同じに確定されれば、1つにまとめる（`outfit_items` は服ごとに1行）。

**3つの段階**

1. **見分ける（AI）**：写真から服・バッグ・小物を見つけ、カテゴリー・種類・色・柄と写真の中の位置を返す。人が複数写っていれば、人ごとに分ける。モデルは既存と同じ系統で始め、精度が足りなければ上位のモデルに上げる（費用は二の次）。
2. **候補を順位付け（ルール）**：見つけたもの1つずつに、手持ちの服（しまった服を除く）から候補を最大5着出す。次の点数を足し、理由も付ける（例：「色と種類が一致」「このデニムとよく合わせている」）。
   - カテゴリーの一致、種類（`subcategory`）の一致、色（`main_color`）の一致。服の側に値がないときは、減点も加点もしない。柄は使わない
   - 色違い・同じ型のグループ
   - セットアップの相方が写っている
   - 他に写っている服と一緒に着た回数
3. **見比べる（AI）**：上位2つの点数差が小さいとき（初期値は、1位の点数の15%未満。定数にして、記録を見て調整する）は、写真の該当部分と候補の服の写真を AI に見比べさせて、順位を調整する。

- 「見分ける」と「見比べる」は差し替えられる部品（インターフェース）にする。今は Gemini、将来はローカルの AI に替えられる。テストではダミーを使う。

**正解率の測り方**

- 「ルールで1位」と「見比べたあとの1位」を分けて記録する。
- 正解率の分母は `matched` の認識だけにする。`registered`（手持ちになかった）、`ignored`、`not_me` は別に件数を数える。

### 7.6 新しい服として登録

- 確認画面で「新しく登録」を選ぶと、サーバーは本人のメディアの行から保存済みの Cloudflare の ID を取り出す。その写真の `analysis` の大きさから、写真の中の位置をもとに服の部分を切り出す。切り出した写真は、今までどおり Supabase の服の写真（`clothing_images`）として保存する。
- 種類や色は AI の結果を初期値にして、それを見て確定してもらう。

## 8. 写真・動画の保存（Cloudflare）

- **写真**：Cloudflare Images。すべての画像を署名付き URL でしか見られないようにする（`requireSignedURLs`）。大きさの種類（バリアント）は3つで、**どのバリアントにも `neverRequireSignedURLs` を付けない**（付けると署名を迂回できるため）。初期設定のときに確認し、テストでも確かめる。
  - `thumb`：一覧用、長辺480px
  - `display`：詳細用、長辺1600px
  - `analysis`：AI 解析と切り出し用、長辺2048px（アップロードは長辺2560px なので、細部が残る）
- **動画**：Cloudflare Stream。`requireSignedURLs` にし、再生もサムネイル（静止画と動くプレビュー）も署名付きトークンでしか見られないようにする。回線に合わせて画質を変えて配信する。一覧ではサムネイルを出し、画面に入ったら音なしで動くプレビューを再生する。
- **署名**：
  - 署名付き URL を作る API は、Cloudflare の ID ではなく、アプリの中のメディア ID を受け取る。
  - サーバーは本人の行を取り出し、保存済みの Cloudflare の ID を使って、短い期限（1時間）で作る。
  - 切り出し、解析、削除も同じ確認を通す。
  - 鍵は環境変数に置く。
- **既存の服の写真**：Supabase Storage のまま。Supabase は DB とログインにも使い続ける。
- **差し替えやすさ**：Cloudflare とのやりとりは1つの部品（MediaStore）にまとめる。テストではダミーを使う。
- **費用**：Images & Stream Starter Bundle（月 $5、2026-10-25 契約）を使う。含まれる量はダッシュボードと API（`images/v1/stats`、`stream/storage-usage`）で確かめる。超えないための対策は 12 章の下の「費用の対策」。
- **プレゼンでの説明**：「着画のメディアは Cloudflare の画像配信と動画配信で、世界中どこでも速く表示する」。

## 9. 画面

### 9.1 メニューと記録

- メニューは Today／Closet／Looks／Loop／My Page の5つのまま。どの画面でも右下に「＋記録」ボタンを浮かべる（一覧の端と少し重なる）。
- 確認待ちのコーデは、Looks のバッジで知らせる。

### 9.2 確認画面

- **本人の選択**：写真に人が複数写っていたら、最初に「どの人がご自身ですか？」と聞き、人をタップしてもらう。選ばなかった人の認識結果は `not_me` にして、候補を選んだ状態にしない。1人だけなら、この段階は飛ばす。
- **見た目**：着画を大きく見せ、写真の上に枠と、確定した服の名前を重ねる。
- **操作**：候補の一覧も常に表示し、上位の候補を最初から選んだ状態にする。当たっていれば「確定」1回で終わる。
- **2つをつなぐ**：写真の枠をタップすると一覧のその行が光り、行を選ぶと写真の枠が光る。
- **配置**：PC では左に写真、右に一覧。スマホでは上に写真、下に一覧。
- **そのほかの操作**：
  - 「＋アイテムを追加」で、AI が見落とした服を足せる。
  - 行ごとに「照合／新しく登録／無視」を選べる。
  - 日付とメモも直せる。

### 9.3 確定直後の演出

- 「確定」を押すと、確認画面が小さなつながりのマップに変わり、今回の服どうしの線が1〜2秒で伸びる。初めての組み合わせは光り、「初めての組み合わせ」と出る。
- タップで閉じるか、そのままマップで遊べる。鏡の前の PC では全画面で見せる。
- `prefers-reduced-motion` のときは、動きを控えめにする。

### 9.4 Looks タブ

1ページに、上から次の順で並べる。

1. 確認待ちのお知らせ
2. つながりのマップの入口カード（開くと、最近よく着ている服が真ん中に来る）
3. よく着る組み合わせ（最近）
4. 月ごとの着画。見出しの右で「写真｜カレンダー」を切り替え、最後に選んだ表示を端末ごとに覚えておく
5. 「去年の○と比べる」（季節の比較）

カレンダー表示の印：

- 確認待ち：橙の点
- 「今日着た」からの提案あり：緑の点
- 記録なし：点線の枠。タップすると、その日付で記録が始まる

写真なしのコーデは、服の写真を並べたタイルで表示する。

### 9.5 季節の比較

- 今の季節の今日までと、去年の同じ範囲（同じ日付まで）を比べる（6.4 章）。
- 次のカードを出す。
  - 増えた
  - 減った
  - 今年の新顔
  - 去年の定番で今年はまだ。「撮ってみる」から記録を始められる
- そのほか、カテゴリーの割合と、去年の同じ季節の着画を出す。
- 下に「つながりのマップで比べる ›」を置き、マップを去年の同じ時期の期間で開く。

### 9.6 服の詳細ページ：つながりのマップ

今の詳細ページ（写真 → 名前 → AI 診断 → 今日着た）の下に入れる。

- **形**：真ん中にこの服、周りに一緒に着た服を置く。回数が多いほど大きく、近く、線が太くなる。カテゴリーごとに方向を分ける。最近一緒に着た線は濃くする。
- **仕掛け（すべて入れる）**
  1. **動かせる**：ドラッグすると線が伸び、離すとばねで戻る。ふだんはふわっと漂う。真ん中の服を動かすと全体がついてくる。
  2. **タップで真ん中が入れ替わる＋来た道**：画面を移らずにたどれる。上のチップで戻れる。
  3. **ピンチで3段階**：
     - カテゴリー：泡にまとまる
     - 服：上位12着を大きく、残りは小さな点
     - 広がり：上位10着それぞれの相手の相手を最大2着、外側に出す
     - ホイール、トラックパッドのピンチ、＋−ボタンでも操作できる。文字は、拡大・縮小しても同じ大きさに保つ。
  4. **たどり方の切り替え**：組み合わせ／入れ替え（同じ役割の服）。
  5. **期間と再生**：
     - 期間は、最近（90日）／去年の同じ時期／全部から選ぶ。
     - ▶ で、最初の記録から今日まで、つながりが育つ様子を週ごとに再生する（6.4 章）。
  6. **長押しで2着の詳細**：一緒に着た回数、最後の日、その2着のコーデの着画。
- **出番待ちの服**：外側に最大5着、薄く浮かべる。真ん中の服と同じカテゴリーは出さず、長く着ていない服を優先する。タップすると「〇〇 × △△、合わせて撮ってみる？」と出て、2着を選んだ状態で記録が始まる。
- **自分で付けた関係**：点線で表示する。
- **しまった服**：印を付けて表示する。
- **「マップ｜一覧」の切り替え**：画面の読み上げを使う人や、正確な回数を見たいときのために付ける。一覧はカテゴリーごとに回数の多い順に並べる。
- 見本：`.superpowers/brainstorm/30486-1792831906/content/relation-map-demo.html`（このデモの動きを本実装の基準にする。ただし再生は、見本の「3か月の枠を進める」ではなく、6.4 章の「育つ様子」にする）。

### 9.7 小さな画面

- **写真なしで記録**：Closet の服をカテゴリーのタブで選び、選んだ服を下にチップで並べる。日付の初期値は今日。1着選ぶと「よく合わせる服」を上に出す。
- **自分で付ける関係**：服の詳細ページの「関係」から「＋追加」を押し、同じ選択画面で服を選ぶ。
- **「今日着た」からの提案**：「今日着た」を押したのにコーデになっていない服があれば、Today のカードに「今日着た3着をコーデにしますか？」と出す。押すと、選択画面が選んだ状態で開く。提案から自動でコーデを作ることはしない。

## 10. エラーの扱い

| 場面 | 扱い |
|---|---|
| カメラの許可がない、カメラがない | 理由を出し、アップロードに切り替える |
| 録画に対応していない | 写真だけ撮る |
| アップロードの失敗、通信が切れる、応答だけ失われる | メディアごとに「もう一度送る」。7.4 章の送り直しの手順で、届いていれば使い、だめなら新しい試行にする |
| アップロード URL の期限切れ | 新しい試行にする |
| Stream の変換の失敗 | メディアを `failed` にし、送り直しか削除を選べる。コーデの記録と解析は続けられる |
| AI の解析の失敗、時間切れ、強制終了 | 実行を `failed` にする（期限切れの `running` も含む）。「もう一度解析」か「手で選ぶ」 |
| 見比べの失敗 | ルールの順位だけで続ける |
| 古い版からの確定・編集 | 拒否して今の状態を返し、画面を最新にする |
| 他人のデータや、別のコーデのデータへの参照 | RPC がエラーを返す。画面には一般的な失敗の言葉だけを出す |
| webhook の署名が不正、時刻が古い | 401 を返し、何も変えない |
| 古い試行の webhook、重複した webhook | 200 を返し、何も変えない |
| Cloudflare の削除の失敗 | 削除待ちのキューで再試行する（6.6 章）。DB の削除は成功として扱う |
| 署名付き URL の期限切れ | 画面を開き直すと作り直す |

### 11.1 計算の部分（`node --test`、TDD で先にテストを書く）

- 関係の計算：入れ替え候補、相手の相手、カテゴリーごとのまとめ、出番待ちの選び方、初めての組み合わせの判定、育つ様子の再生の区切り（週ごと／日ごと）。
- 季節の比較のハイライト。

- `confirm_outfit` に渡す差分の計算（足す・外す・日付の変更）。
- 正解率の集計（ルールの1位と見比べ後の1位、分母の決め方）。
- Cloudflare：
  - 署名付き URL とトークンの作成（鍵と時刻を固定）
  - webhook の確認（正しい署名、本文の改変、不正な署名、古い時刻、古い試行の ID、重複）

### 11.2 DB（Docker の Postgres、`supabase/tests/run-0XX.sh`）

| 領域 | テスト |
|---|---|
| 権限 | `wear_logs` への直接の追加・更新・削除の拒否。`clothing_items` の派生値とアーカイブ列を、追加のときも更新のときも指定できない。内部用とサーバー専用の関数（`rebuild_*`、`register_outfit_media` など）を `authenticated` からも `anon` からも呼べない（`PUBLIC` からの継承も含めて、実際に呼んで拒否されることを確かめる）。他人の行を読めない・書けない |
| 公開とアーカイブ | しまった服を `is_public = true` にしようとすると CHECK 制約で失敗する |
| 関連の整合性 | 他人の服・メディア・認識結果・着用記録の拒否。同じ本人の**別のコーデ**のメディア・認識結果・着用記録を混ぜる要求の拒否 |
| 確定と編集 | 初めての確定、同じ内容の送り直し、古い版からの送り直しの拒否、服を足す・外す、月をまたぐ日付の変更。`wear_count` と `last_worn_at` が残っている記録と一致する。`wear_today` の記録を再利用し、外しても残る |
| 同時実行 | **2つの DB 接続**から同時に確定する。確定と「今日着た」の競合。同じ着用記録の二重利用が起きない |
| 集計 | 最後の元データを消した月の行が消える。全期間の作り直しが、少しずつ更新した結果と一致する。既存の着用記録からの初期集計 |
| 削除 | しまう・戻す。完全な削除で、コーデが残り、ほかの服の組み合わせが残り、サマリーが作り直される。コーデに入っている服の直接削除を DB が拒否し、作ったばかりの服の削除は通る。コーデを消すと `wear_today` の記録が残る |
| 解析 | 古い実行の結果を保存できない。1つのコーデで実行中は1つまで。期限切れの `queued` と `running` が `failed` になり、もう一度解析できる。代表の写真を変えると、古い実行が `canceled` になり、新しい実行が今の実行になる |
| 削除待ち | 削除のときに必ずキューに入る。2つの接続から同時に取り出しても二重にならない。取得権（`claim_token`）が違う処理は結果を書き込めない。期限（`lease_until`）を過ぎた行は取り出し直せる |
| 既存機能 | 服の登録・編集・公開・「今日着た」・登録失敗の取り消しが、権限の変更後も動く |

### 11.3 差し替え部品

- 「見分ける」「見比べる」「MediaStore」はダミーで試す。
  - ダミーの認識結果から、候補の順位と判断の記録が保存されるか。
  - アップロードの応答が失われたときに、実体を確かめて再利用するか。期限切れのときに、新しい試行に移って古い ID を削除待ちに入れるか。
  - 同じメディア ID で「開始」が2回来たときに、メディアが1つのままか。URL の発行のあと DB への保存に失敗したときに、Cloudflare の ID を消しにいくか。
  - 解析が途中で止まったときに、期限のあとで `failed` になるか。代表の写真を変えたあとの古い結果を捨てるか。
  - 削除処理が二重に動いても大丈夫か。Cloudflare の 404 を成功として扱うか。
- 本物の Gemini と Cloudflare は、`scripts/test-image-analysis.mts` のような手動スクリプトで確かめる。
  - サンプルの着画で、1位の候補の正解率を測る。
  - 署名なしでは写真・動画・サムネイルを見られないこと。
  - バリアントに `neverRequireSignedURLs` がないこと。

### 費用の対策

- Stream の保存の枠は前払いで、超えると新しい動画を送れなくなるだけで、追加の料金にはならない。
- 動画の長さの上限は60秒にする。アップロード URL の期限は30分（送られなかった URL が保存の枠を長く使わない）。
- 消したメディアは、削除待ちの処理（6.6 章）で Cloudflare から必ず消す。確認用のスクリプトも、作ったものを最後に消す。
- 画像の変換（Image Transformations、Media Transformations）は使わない。大きさの種類は Images のバリアントだけで作る。
- 配信の量は、ダッシュボードの Billing と Stream の画面で、週に1回確かめる。

## 13. 将来への備え

- **同期**：新しいテーブルは UUID と作成日時・更新日時を持つ。サマリーは事実から作り直せるので、同期するのは事実だけで済む。
